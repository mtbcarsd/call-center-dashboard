# История проекта и куда развиваться

Сжатая хронология ключевых архитектурных решений — не построчный пересказ
журнала сессий, а то, что важно понять о том, **почему** система устроена
именно так. Подробности каждого перехода — в `git log` репозитория.

## Хранилище: Snowflake → SQLite → PostgreSQL

Проект начинался на Snowflake (облачный DWH с Cortex LLM-функциями), но
триальный аккаунт не давал доступа к нужным Cortex-функциям, а при смене
пароля учётная запись оказалась временно заблокирована — вместе с находкой,
что пароль был захардкожен и уже запушен в публичный репозиторий. Решение:
полностью отказаться от Snowflake, перейти на локальный SQLite (без облачных
credentials вообще). Когда встал вопрос деплоя на Railway — SQLite не
годился (эфемерная файловая система), поэтому финальный переход на
PostgreSQL с персистентным диском. Подробная схема — [База данных и
хранилище](database.md).

## LLM: локальный Ollama → облачный Groq для прода

`agents/base.py` изначально писался под локальный Ollama — решение, чтобы
демо не зависело от GPU/облачных credentials на этапе разработки. Общий
контракт (OpenAI-совместимый `base_url`) сразу заложил переключение через
`.env` без изменений кода — когда Railway Trial-план (1GB RAM/сервис)
оказался мал для Whisper+pyannote+Ollama одновременно, прод переключился на
Groq простой сменой `LLM_BASE_URL`/`LLM_API_KEY`, без правки агентов.
Апгрейд на Railway Hobby-план (2026-07-18) снял RAM-ограничение и для
`api` — Groq в проде используется не потому, что RAM всё ещё не хватает, а
потому что уже был настроен и работал, когда апгрейд состоялся.

## Дашборд: Streamlit → Plotly Dash

Исходный Streamlit-дашборд (`dashboard.py`) рос органически, вкладка за
вкладкой (Phase 1-3 в терминологии проекта), с единственным хардкоженным
пользователем-админом без ролевого разделения. Мотив перехода на Dash — не
техническая жалоба на Streamlit, а презентационная задача (нужны были более
сильные визуально графики) в сочетании с давно отложенной идеей
(«персональный кабинет оператора» из анализа конкурента) — миграция
объединила обе задачи: три ролевых дашборда (executive/manager/employee) на
Dash, с настоящей таблицей `users`+bcrypt вместо dict. Полный план по фазам
(D1-D5) — `DASH_MIGRATION_PLAN.md` в репозитории; миграция завершена
2026-07-24 мягким cutover — Dash стал основным, Streamlit оставлен жить как
страховка на откат, без назначенного срока отключения.

После завершения D1-D5 дашборд продолжил расти уже без формального
фазового плана — по мотивам конкретных референсных дашбордов
(geckoboard.com, `dash-manufacture-spc-dashboard`, `dash-clinical-analytics`):
тренды и алерты на «Аналитике», control chart на «Операторах», annotated
heatmap на «Compliance». Подробности — [Dash-дашборд](dashboard.md).

## Куда развиваться

Актуальный бэклог и его приоритеты меняются быстрее, чем эта страница
успевала бы за ними — единственный источник правды: `README.md` → «Куда
развиваться» в репозитории (там же — история того, что из бэклога конкурента
MeliSSA уже закрыто, а что нет) и `NEXT_SESSION.md` (конкретные варианты на
следующую сессию с уже согласованными решениями). Не дублируется здесь,
чтобы не расходиться при обновлении одного без другого.
