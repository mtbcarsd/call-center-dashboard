# Пайплайн анализа звонков

Общая логика анализа одного звонка — от аудиофайла до JSON-контракта с
классификацией, чек-листом, compliance и резюме. Как этот контракт
используется тремя фасадами (`pipeline.py`/`webui_pipeline.py`/`api/main.py`)
— см. [Архитектура и обзор системы](architecture.md). Здесь — что происходит
внутри общего слоя: ASR, диаризация, 4 агента + два бонусных агента,
чек-лист.

## ASR: транскрипция и диаризация

**`asr/transcriber.py`** — обёртка над `faster-whisper` (модель `medium`,
`device="cpu"`, `compute_type="int8"` — работает без GPU). `Transcriber.run()`
возвращает сегменты (`start`/`end`/`text`), полный текст, определённый язык,
длительность и метрики пауз (`compute_pause_metrics()`): суммарное время пауз
между репликами длиннее 2 секунд (`PAUSE_THRESHOLD_SEC`), их количество и
доля от длительности звонка (`silence_pct`) — прокси-метрика того, насколько
гладко шёл разговор.

**`asr/diarizer.py`** — определяет, кто из двух спикеров оператор, а кто
клиент. Whisper даёт сегменты речи без привязки к говорящему; `pyannote`
(`pyannote/speaker-diarization-3.1`, предобученная модель) независимо
определяет временные интервалы речи каждого спикера. Сегмент Whisper
относится к тому спикеру `pyannote`, с которым у него наибольшее пересечение
по времени (`_overlap()`). Кто из двух спикеров — оператор, решается
эвристикой: ищем приветственную фразу (`GREETING_WORDS` — «здравствуйте»,
«добрый день», «банк», «чем могу помочь» и т.п.) среди первых 3 реплик; если
не нашли — оператором считается тот, кто говорит первым (стандарт для
входящих звонков банка). `operator_talk_ratio()` считает долю времени
разговора, которую говорил оператор.

:::{note}
Технический нюанс: `pyannote` 4.x по умолчанию использует `torchcodec`,
которому нужен ffmpeg 4/5 (`libavutil.so.56/57`); в окружении проекта стоит
ffmpeg 6 (`so.58`). Поэтому waveform загружается напрямую через `librosa`, а
не через `torchcodec` — обходит несовместимость целиком.
:::

## Оркестрация: 4 независимых агента параллельно

`orchestrator.py` запускает 4 агента через `asyncio.gather` и собирает единый
JSON-контракт (подробно — почему `asyncio.gather`, а не LangGraph — см.
[Архитектуру](architecture.md#supervisor-vs-langgraph)). Каждый
агент — простой наследник `agents/base.py::BaseAgent`, задающий только два
метода:

- `build_prompt(transcript, **kwargs)` — собирает промпт (транскрипт
  обрезается до 3000 символов — укладывается в контекст локальной модели);
- `fallback()` — что вернуть, если LLM недоступна или ответ не парсится в
  JSON (`extract_json()` вытаскивает JSON даже из ответа, обёрнутого в
  markdown-блок или с лишним текстом вокруг).

`BaseAgent.run()` сам обрабатывает ошибки — при любом исключении (сеть, таймаут,
невалидный JSON) агент не падает, а возвращает `fallback()`, плюс пишет
JSON-лог с `agent`, `elapsed_ms`, `parse_failed` и текстом ошибки. Это
единственная точка, где нужно отлаживать проблемы с LLM-провайдером — не в
каждом агенте по отдельности.

### Четыре основных агента

| Агент | Файл | Возвращает |
|---|---|---|
| Классификатор | `agents/classifier.py` | `topic` (кредиты/карты/переводы/жалобы/другое), `priority`, `customer_intent` |
| Качество | `agents/quality.py` | `checklist` (см. ниже) + взвешенный `total` (0-100) |
| Compliance | `agents/compliance.py` | `passed`, `issues` — regex-проверка + LLM-проверка обязательных дисклеймеров |
| Суммаризатор | `agents/summarizer.py` | `summary`, `action_items`, `resolution_status`, `customer_satisfaction_score`, `escalation_flag`, `key_topics` |

**Compliance** — единственный агент, который совмещает LLM-проверку с
детерминированными regex-правилами (`FORBIDDEN_PATTERNS` — обещания
гарантированного дохода, «100% без риска», оскорбления клиента). Итоговый
список нарушений — объединение regex-совпадений и того, что нашла LLM;
`passed = True` только если нарушений нет вообще. Список фраз — иллюстративный
стартовый набор, для боевого использования нужно согласование с реальным
compliance-отделом банка.

**Quality** — единственный агент, который переопределяет `run()` целиком, а
не только `build_prompt()`/`fallback()`: после ответа LLM (набор true/false по
каждому пункту чек-листа) он же считает взвешенный итог через
`checklist.weighted_score()`.

### Два бонусных агента — работают не с одним транскриптом

**`agents/trends.py`** и **`agents/coaching.py`** отличаются от четырёх
основных тем, что не анализируют транскрипт заново — работают с уже
посчитанным агрегатом:

- `analyze_trends(calls)` — берёт резюме и темы последних N звонков (данные
  из Postgres, `GET /trends`), ищет повторяющиеся паттерны/проблемы для
  супервайзера.
- `analyze_coaching(operator_name, stats)` — берёт агрегированную статистику
  по звонкам конкретного оператора (средняя оценка, % прохождения по каждому
  пункту чек-листа, встречавшиеся compliance-нарушения — `GET
  /coaching/{operator_name}`), формирует персональные сильные/слабые стороны
  и рекомендации по обучению.

Оба — источник LLM-функций Dash-дашборда (страницы «Тренды» и «Мой кабинет»),
не часть batch-анализа каждого звонка.

## Чек-лист: конфигурируемая оценка вместо одного числа от LLM

`checklist.py` — вместо того, чтобы просить LLM сразу выдать оценку 0-10
(субъективно и непрозрачно), чек-лист задаёт 6 да/нет вопросов с весами,
сумма которых равна 100:

```python
CHECKLIST = [
    {"key": "greeting", "label": "Приветствие", "weight": 15, "question": "..."},
    {"key": "needs_discovery", "label": "Выявление потребности", "weight": 20, "question": "..."},
    {"key": "solution_presented", "label": "Предложено решение", "weight": 20, "question": "..."},
    {"key": "objection_handling", "label": "Отработка возражений", "weight": 15, "question": "..."},
    {"key": "politeness", "label": "Вежливость и тон", "weight": 15, "question": "..."},
    {"key": "closing", "label": "Прощание", "weight": 15, "question": "..."},
]
```

`weighted_score()` считает взвешенный итог 0-10 по ответам LLM. Сейчас список
захардкожен в коде — редактирование пунктов/весов требует правки Python и
редеплоя; конфигурируемый через UI чек-лист (без правки кода) — идея из
анализа конкурента, см. [История проекта](history.md).

Там же — общие функции парсинга сохранённого в БД `checklist_json`/
`compliance_json` (`parse_checklist`, `parse_compliance`,
`checklist_pass_rates`): единый источник вместо дублирования в
`dashboard.py` (Streamlit) и `dash_app/` (Dash).

## Сквозной пример: от аудиофайла до записи в БД

Так `pipeline.py` обрабатывает один файл (тот же порядок шагов справедлив и
для `api/main.py::POST /analyze`, только на один файл за раз, без записи в
Postgres):

1. **`transcribe_all()`** — обходит `audio_original_data/<отдел>/*.wav`
   (отделы обнаруживаются автоматически по имени подпапки), для каждого
   файла: `Transcriber.run()` → сегменты + текст + метрики пауз, `diarize()`
   → метка оператор/клиент на каждый сегмент, `operator_talk_ratio()`,
   `storage.upload_audio()` → аудио в Railway Bucket, получаем `audio_key`.
2. **`analyze_all()`** — для каждого транскрипта вызывает
   `orchestrator.analyze(transcript_text)`, разбирает результат в плоский
   словарь полей будущей записи `call_analysis` (`call_type`, `urgency`,
   `customer_intent`, `resolution_status`, `agent_performance_score` —
   `quality_score.total / 10`, `checklist`, `compliance`, `action_items`, …).
3. **`upload_to_db()`** — три таблицы одним проходом: `ai_transcribed_calls`
   (сырой транскрипт), `call_analysis` (вся аналитика, JSON-поля через
   `json.dumps(..., ensure_ascii=False)` — чтобы кириллица не превращалась в
   `\uXXXX` в БД), `call_segments` (реплика × спикер, для перемотки плеера по
   клику в Dash-дашборде).

Перед загрузкой в БД результат анализа сохраняется в `results_cache.json` — на
случай, если сам `upload_to_db()` упадёт (например, недоступна БД), не нужно
повторять транскрипцию+анализ заново (`upload_from_cache.py` грузит уже
готовый кэш).

**Важно:** `upload_to_db()` начинается с `DELETE FROM
ai_transcribed_calls/call_analysis/call_segments` — полный прогон
`pipeline.py` пересчитывает и перезаписывает **все** звонки. Для точечного
добавления новых звонков без потери уже накопленных ручных правок (теги,
операторы, `qa_score`, комментарии) используются отдельные INSERT-only
скрипты — см. [Скрипты и вспомогательные утилиты](scripts.md).
