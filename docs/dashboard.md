# Dash-дашборд

`dash_app/` — основной публичный дашборд (см. [Dash-дашборд как потребитель](
architecture.md#dash-as-consumer)). Точка входа — `dash_app/app.py`
(`gunicorn dash_app.app:server` на Railway), `use_pages=True` — каждая
страница регистрируется через `dash.register_page()` в своём модуле
`dash_app/pages/*.py`.

## Аутентификация и роли

Логин — обычный Flask-роут (`/login`, `POST`), не встроенный механизм Dash:
рендерит статичный HTML-шаблон напрямую (`render_template_string`), проверяет
пароль (`bcrypt` через `dash_app.auth.verify_password`) и кладёт пользователя
в Flask `session` (`username`/`role`/`display_name`/`department`/
`operator_match_name` — те же поля, что в [таблице `users`](
database.md#users-table)). `server.secret_key` — из `DASH_SECRET_KEY` или
случайный на каждый рестарт процесса (сессии не переживают передеплой — это
осознанно ок для этого масштаба).

`@server.before_request` (`_require_login`) защищает все роуты разом:

- без сессии — редирект на `/login?next=<путь>`;
- `role=employee` — редирект на `/me` с любого пути, кроме
  `/me`/`/help`/`/login`/`/logout` (и статики `/_dash`/`/assets`). Это не
  просто скрытый пункт меню — остальные страницы показывают агрегаты и
  данные **других** операторов (рейтинг, compliance по именам), так что для
  сотрудника это реальная защита от утечки, а не только UX.

Навигация (`_DIRECTOR_NAV_LINKS`/`_EMPLOYEE_NAV_LINKS` в `app.py`) и её
подсветка активного пункта пересчитываются `@callback` на `Input("url",
"pathname")` — тот же паттерн для всех страниц, не хардкод на сервере.

**Важно:** route guard решает, *какие страницы* доступны, но не гарантирует
сам по себе, что данные на разрешённых страницах отфильтрованы по роли —
это отдельный слой (department/operator_match_name-скоуп в `dash_app/data.py
::load_calls()`), применяемый на уровне каждого запроса к БД, а не один раз
на входе. См. «Защита данных внутри callback'ов» ниже.

## Светлая/тёмная тема

Переключение полностью clientside — нет смысла гонять выбор темы на сервер и
обратно:

- Цвета UI-хромы (`dash_app/colors.py::COLORS`) указывают на CSS custom
  properties (`var(--paper)`, `var(--surface)`, …), сами `--x` определены
  один раз в `app.index_string` — `:root` для светлой темы,
  `@media (prefers-color-scheme: dark)` как системный фолбэк,
  `[data-theme="dark"]`/`[data-theme="light"]` побеждают в обе стороны при
  ручном переключении.
- `dash.clientside_callback` на кнопке-переключателе читает/пишет
  `data-theme` на `<html>` и **сразу** в `localStorage['theme']` — не через
  `dcc.Store`, чтобы не зависеть от внутреннего формата сериализации Dash.
- Anti-FOUC: синхронный `<script>` в `<head>` (до отрисовки тела) выставляет
  `data-theme` из `localStorage`/`prefers-color-scheme` ещё до первого рендера
  — без этого была бы заметна вспышка светлой темой перед тем, как отработает
  clientside callback.
- **Plotly-графики и семантические акценты (success/warning/danger/
  `kpi_*`/`urgency_*`) не перекрашиваются вместе с темой** — Plotly не умеет
  резолвить `var(...)`, поэтому эти цвета остаются фиксированным hex
  (`dash_app/components/gauge_tile.py` красит число и `bar.color` в реальный
  hex статуса, а не в `COLORS["text_primary"]`, которая на самом деле
  CSS-переменная). На странице «Аналитика» три Plotly-графика сознательно
  оставлены светлыми «островами» на тёмной странице — trade-off вместо
  per-chart clientside-регенерации фигур.

## Страницы

| Путь | Название | Кому видна | Что показывает |
|---|---|---|---|
| `/` | 📊 Аналитика | executive, manager | Hero-KPI (оценка оператора, % решено), лидерборд топ/анти-топ операторов, проактивные пороговые алерты (без LLM), тренды по дням (7-дн. скользящее среднее) с фильтром периода и сравнением к предыдущему, разбивка по темам/срочности/отделам, сводная таблица. Автообновление 90 сек |
| `/calls` | 📁 Звонки | executive, manager | Галерея карточек (с фильтром «только с аудио», порционная подгрузка), деталка со плеером, перемоткой по клику на реплику, инлайн-редакторами (тип/оператор/QA-оценка), тегами/коллекциями, комментариями |
| `/operators` | 🧑‍💼 Операторы | executive, manager | Построчный список со спарклайном тренда оценки и шкалой «% ниже нормы», клик раскрывает control chart (норма команды = среднее ±1.5σ), донат по проблемным звонкам, quick-stats шапка. Автообновление 90 сек |
| `/rating` | 🏆 Рейтинг | executive, manager | % прохождения по каждому пункту чек-листа (общий + по операторам), предупреждение при худшем пункте < 50% |
| `/compliance` | 🛡️ Compliance | executive, manager | Annotated heatmap нарушений (дни недели × недели периода) с drill в таблицу по клику, фильтр по типу нарушения + диапазону дат, разбивка по операторам |
| `/trends` | 📈 Тренды | executive, manager | LLM-паттерны по последним N звонкам (слайдер), запрос к `GET /trends` на сервисе `api` |
| `/team` | 👥 Команда | executive, manager | Статический состав команды разработки (не операторов) |
| `/me` | 🙋 Мой кабинет | **только employee** | Только звонки этого оператора (`operator_match_name`), свой чек-лист, кнопка «Получить рекомендации» → `GET /coaching/{operator_name}` |
| `/help` | ℹ️ Справка | все роли | Статический тур по страницам + честное сравнение с конкурентом (не БД) |

Везде, где страница видна и `executive`, и `manager` — данные для `manager`
сужены сервером до его отдела (`get_current_department()` → `load_calls
(department=...)`), а не спрятаны на клиенте.

## Компоненты (`dash_app/components/`)

- **`stat_tile(label, value, subtitle=None, accent=..., delta=None)`** —
  замена `st.metric()`: простое число/строка с акцентной левой полосой.
- **`gauge_tile(label, value, good=, warn=, max_value=100, unit="%",
  decimals=0, size="md"|"lg", delta=None)`** — полукруглый `go.Indicator` с
  цветовым порогом (зелёный/жёлтый/красный по `good`/`warn`). `max_value`/
  `unit`/`decimals` появились в фазе E, чтобы тот же визуальный язык
  «полукруг + порог» подходил не только для 0-100%, но и для оценок 0-10
  (hero-ряд на «Аналитике»); `size="lg"` — увеличенный вариант для hero-ряда.
- **`delta_badge(delta, unit="", up_is_good=True, decimals=1)`** — бейдж
  ▲/▼ сравнения с предыдущим периодом; `None` при отсутствии данных (не
  «н/д» — обычный случай для «Всё время»/начала сбора данных); направление
  «хорошо/плохо» задаётся явно (`up_is_good`), не выводится из знака дельты
  (рост эскалаций — плохо при том же положительном знаке, что и рост оценки).
- **`page_header(icon, title, subtitle=None)`** / **`section_header(text)`**
  — единый заголовок страницы (eyebrow + serif) и заголовок секции внутри
  карточки (sans, не serif — секции сканируются, а не читаются).
- **`cell_format.py`**: `pct_cell()`/`score_cell()` — общий ag-grid
  `valueFormatter` (🟢/🟠/🔴 + число) вместо того, чтобы каждая страница
  держала свой `_PCT_STYLE`/`_SCORE_STYLE`; `score_dot()` — тот же порог как
  чистая Python-функция для мест без JS-рантайма ag-grid (карточки галереи).

`dash_daq` как зависимость не используется — все «приборные» виджеты
(градиентная шкала, спарклайн) собраны на `html.Div`/`dcc.Graph` и уже
существующих компонентах, чтобы не заводить вторую систему темизации, не
подхватывающую `data-theme`.

## Паттерны разработки

### `layout()`-оболочка + `@callback` вместо монолитного `layout()`

Страницы с интерактивной перерисовкой (`analytics.py`, `calls.py` — галерея,
`operators.py`, `compliance.py`) разделяют статичную часть (шапка, фильтры,
пустой контейнер) в `layout()` и содержимое — в `@callback`, который
перерисовывает только контейнер по `Input` (диапазон дат, фильтр,
`dcc.Interval`). Не вся страница целиком — быстрее и не сбрасывает состояние
виджетов фильтра при каждом обновлении.

### `dcc.Store` вместо состояния кнопок

Там, где список кнопок сам может быть перерисован (например, `dcc.Interval`
каждые 90 сек на «Операторах»), выбор пользователя хранится в `dcc.Store`
(`operators-selected-op`, `calls-selected-file`, `compliance-selected-cell`),
а не читается из `n_clicks` конкретной кнопки напрямую. Иначе каждое
обновление по интервалу пересоздаёт кнопки со сброшенным `n_clicks`, и
drill-down остаётся привязан к уже не существующему экземпляру кнопки.

### Pattern-matching id: ключ — строка, не число

`{"type": "operator-row-btn", "name": name}` (имя оператора) и
`{"type": "open-call-btn", "index": file_name}` — ключ строковый. Числовой/
float-ключ в pattern-matching id — известный источник бага в проекте (ловил
`JSON.parse` на стороне dash-renderer при сравнении `time_cs` как float,
см. `calls_logic.py`) — везде, где это возможно, используются человекочитаемые
строки, а не индексы.

### `layout(**_query_params)` для страниц, принимающих query-параметры

`dash.page_container` передаёт query-параметры URL как kwargs в `layout()`
каждой страницы. Сигнатура `def layout()` без аргументов падает с `TypeError:
unexpected keyword argument` на переходе вида `/operators?op=...` — сигнатура
должна принимать `**_query_params`, даже если сам параметр читается позже
через `Input("url", "search")` (единственный глобальный `dcc.Location(id=
"url")`, объявленный в `app.py`), а не через сами kwargs.

### Drill-in между страницами через markdown-ссылку в ag-grid

Таблицы «По операторам» на `rating.py`/`compliance.py` рендерят имя
оператора как markdown-ссылку `[{name}](/operators?op={quote_plus(name)})`
(`cellRenderer: "markdown"` в columnDef) — открывает тот же control chart на
`/operators`, что и клик по строке на самой странице, без дублирования
рендер-логики (`_render_detail()` вызывается из обоих путей).

### `clientside_callback` там, где Python не может управлять DOM напрямую

Единственные два места в проекте: перемотка `<audio>` по клику на реплику
(`currentTime` — не controllable Dash-проп `html.Audio`, JS находит элемент
по id и двигает playhead) и переключатель темы (см. выше). Оба —
осознанное исключение из общего правила «логика на сервере», а не стиль по
умолчанию.

### Промежуточный `dcc.Store` вместо прямого чтения `clickData` того же графика

Compliance-heatmap: колбэк, который перерисовывает `figure` графика, не
может сам же напрямую слушать `clickData` этого графика — Plotly.js на
клиенте иногда делает частичное обновление трейсов при одновременном
срабатывании figure-`Output` и `clickData`-`Input` одного и того же графика,
и heatmap визуально ломается (цвета/аннотации съезжают в угол). Фикс —
промежуточный `dcc.Store` (`compliance-selected-cell`): один колбэк только
читает `clickData` и пишет в `Store`, другой перерисовывает `figure`,
слушая `Store`, не `clickData` напрямую. Тот же приём, что `calls-selected-
file` в `calls.py`.

### Явный `type="category"` на осях с датоподобными строками

Там же: `x`-значения heatmap — строки вида `"2026-06-01"` (ISO-подобные).
Без явного `type="category"` Plotly.js после клика по ячейке иногда
переопределяет тип оси на `"date"`, и уже отрисованные аннотации
(привязанные к категориальным позициям) съезжают при следующем обновлении
figure.

### Защита данных внутри callback'ов, не только на входе в страницу

`calls.py::_file_in_scope()` — каждый save-колбэк (сохранение типа/
оператора/QA-оценки/тегов/комментария) отдельно проверяет, что `file_name`
всё ещё входит в department-скоуп текущего пользователя, **до** записи в
БД — а не полагается на то, что раз пользователь видит страницу, то он не
может обратиться с чужим `file_name` (прямым вызовом callback, подменой
данных в `dcc.Store` через devtools). Тот же принцип, что route guard
верхнего уровня, но применён на уровне каждой мутации, не только чтения.
