# Скрипты и вспомогательные утилиты

## Главное правило: как добавлять новые звонки

`pipeline.py::upload_to_db()` начинается с `DELETE FROM
ai_transcribed_calls/call_analysis/call_segments` — **полный прогон
пересчитывает и перезаписывает вообще все звонки**, включая уже накопленные
ручные правки (теги, `operator_name`, `qa_score`, комментарии, `call_type_
override`). Поэтому для точечного добавления новых звонков используются
отдельные **INSERT-only** скрипты, которые не трогают существующие строки:
`scripts/add_new_calls.py` — канонический пример этого паттерна.

Если понадобится добавить ещё звонков — новый скрипт по этому же образцу, не
повторный запуск `pipeline.py`.

## `scripts/seed_users.py` — учётные записи

Создаёт начальных пользователей в таблице `users` (см.
[База данных](database.md#users-table)): `julia` (executive),
`boss_oo`/`boss_orkki` (manager, свой отдел), `sokolova` (employee, личный
кабинет с `operator_match_name`). Пароли хешируются `dash_app.auth.
hash_password` (bcrypt). Идемпотентен — `ON CONFLICT (username) DO NOTHING`,
безопасно перезапускать; чтобы поменять пароль существующего пользователя,
нужен отдельный `UPDATE`, не повторный запуск скрипта.

## `scripts/generate_synthetic_calls.py` — тестовые звонки для WER

Генерирует синтетические аудиозаписи через `edge-tts`
(`ru-RU-SvetlanaNeural` — оператор, `ru-RU-DmitryNeural` — клиент, паузы
~0.6с между репликами) в `test_data/` — сценарии покрывают те же категории,
что ожидает `agents/classifier.py` (кредиты/карты/переводы/жалобы/другое).
Смысл существования: реальные записи (`audio_original_data/`) не
публикуются (см. `.gitignore`), а требование ТЗ («5+ аудио с эталонными
транскриптами в репозитории») закрывается безопасной для коммита синтетикой.

## `scripts/compute_wer.py` — оценка качества транскрипции

Прогоняет `Transcriber` по всем `test_data/*.wav`, считает WER (`jiwer`)
против эталонных `.txt`-транскриптов того же сценария (включая `_8khz`-
варианты — то же эталонное содержание, другое качество звука) и пишет отчёт
в `test_data/wer_report.md`.

## `scripts/add_new_calls.py` — INSERT-only добавление звонков

Сгенерировал и загрузил 10 звонков (5 вымышленных операторов на отдел) с
собственным `call_datetime` у каждого — впервые в проекте звонки с разным
временем, не одним batch-прогоном. Полностью прогоняет реальный пайплайн
(Whisper + pyannote + 4 агента), не имитирует результат. Безопасно
перезапускать: пропускает файлы, для которых аудио или запись в БД уже есть.
Пишет и в локальную, и в Railway Postgres (`RAILWAY_DATABASE_PUBLIC_URL` из
окружения, не хардкод).

## `scripts/fix_new_calls_analysis.py` — восстановление после сбоя LLM

Разовый скрипт под конкретный инцидент: при первом запуске
`add_new_calls.py` в системе не хватило RAM для Ollama (torch/whisper/
pyannote всё ещё висели в памяти), все 10 звонков получили пустой fallback-
анализ («Анализ недоступен», чек-лист весь `false`). Транскрипция и
диаризация в кэше (`new_calls_cache.json`) были посчитаны верно, поэтому
скрипт **не импортирует `asr/`** (`torch`/`whisper`/`pyannote` вообще не
загружаются) — только `orchestrator`/`agents`, оставляя намного больше
свободной RAM под Ollama. Пересчитывает 4 агента из уже сохранённого
транскрипта и делает `UPDATE` уже вставленных строк (не `INSERT`).

Общий урок из этого инцидента: если на машине одновременно работают
torch/whisper/pyannote-процесс и Ollama, RAM легко становится боттлнеком —
скрипт восстановления, который явно не тянет тяжёлые ML-зависимости, там,
где они не нужны, экономит и время, и память.

## `scripts/generate_synthetic_metrics_calls.py` — облегчённая синтетика для графиков по времени

320 звонков **напрямую в `call_analysis`, без синтеза аудио и без прогона
через LLM-пайплайн** — только правдоподобный разброс `call_datetime` по ~90
дням (будни > выходных, пик 9-11/15-16) и метрики, смоделированные по
образцу распределений в реальных данных. Формулы согласованы с реальным
пайплайном: `agent_performance_score == checklist.weighted_score(checklist_
json)` — не отдельная, рассинхронизирующаяся логика. Остальные поля
(`customer_satisfaction`, `escalation_flag`, `compliance_json`) в реальном
пайплайне — независимые LLM-суждения без жёсткой формулы, поэтому здесь
смоделированы с правдоподобной корреляцией к «скиллу» оператора, а не по
точной формуле.

**Пишет только в локальную Postgres** — на Railway сознательно не заливалось
(явное решение с пользователем). Звонки этой генерации не имеют ни аудио
(`audio_key IS NULL`), ни транскрипта (`transcript_text IS NULL`) —
используются страницами «Аналитика» (тренды по дням) и «Compliance»
(heatmap по дням/неделям), см. [Dash-дашборд](dashboard.md).
